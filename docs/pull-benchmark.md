# Pull baseline and bounded child concurrency (issue #363)

`aw pull` remains serial by default (`--jobs 1`). `aw pull --jobs 4` permits at most four independent child repositories to pull concurrently, after the workspace parent has completed, configuration is reloaded, and managed-ignore reconciliation finishes. `--jobs` accepts a positive safe integer; `-j` remains JSON output. When Git common-directory and physical path independence cannot be proven, the command falls back to the serial path without introducing a probe error. Output is buffered in configured order; a failed or manual-update child stops queued claims and already-started children finish before the summary. Hook/rollback work remains sequential inside each repository.

The benchmark case is **opt-in** and separate from `pnpm benchmark`. Build the exact starting executable with `pnpm build`, copy it to an immutable location before making runtime changes, then run:

```sh
pnpm benchmark:pull:run -- --binary /path/to/pinned/arashi.bin --binary-source-head <full-source-commit-sha> --warmup 1 --iterations 7 --output benchmark-results/pull-base.json
```

The Node runner invokes the direct compiled Bun executable, not the npm shim or a source adapter. For the concurrent candidate pass `--jobs 4` to this runner; it records `pull --json --jobs 4` as the invoked command. The serial base remains `pull --json`. It creates fresh `small` (parent + 2 children, 2 coordinated child worktrees) and `large` (parent + 8 children, 40 coordinated child worktrees) fixtures with the existing benchmark topology and isolated Git/home environment. Every parent and child has one real commit on a local filesystem `origin/main`, not merely an empty fetch. Before each warm-up and sample, local heads are reset to the fixed prior commits; after each invocation, every head and marker is checked against its remote. Parent configuration remains tracked and is reloaded after its pull. Output assertions require parent-first configured order, all `updated` statuses, and overall success. Raw stdout, every JSON field (including timing and Git output), exit success, CPU availability, sorted wall samples, median, nearest-rank p95, fixture commit fingerprint, binary SHA-256/size, runner and invocation runtimes, and host platform are recorded. An executable mutation during measurement aborts. The runner does **not** silently exclude volatile fields or claim Git process-count instrumentation; compiler provenance is explicitly unavailable for a prebuilt artifact.

Only compare artifacts with identical fixture fingerprint, topology and case version, platform/toolchain, command boundary, warm-up and iteration settings. A separate candidate binary can use the same adapter via `--binary`. For semantic parity compare full result structures and raw output, except actual elapsed durations and the fixture-owned absolute root path in Git's `From` diagnostics; report those exclusions explicitly rather than deleting any behavior field. Fixture commit IDs are deterministic, but temporary root paths vary. Run candidate and base interleaved on the same machine if load drift matters. These controlled local remotes do not model hosting-provider latency. No hosted CI wall threshold should be introduced from this baseline.

Pinned artifact SHA-256: `e61a991390e21b425a0b1ec30dd7424daa9375e0e7ee7f278b1a04f463fd817f`. Raw baseline JSON and pinned executable are in `/Users/corwin/.hermes/cache/scratch/arashi-363-pull/` (scratch retention is temporary). The measurement is serial baseline only; no candidate speedup is asserted. The child I/O contribution grows substantially at large scale, so bounded pull-only concurrency merits an implementation experiment. Keep the parent sequential, freeze the post-parent plan, prove independence and failure/drain semantics, and stop if exact-binary same-fixture comparison fails to show meaningful large-workspace gain or violates parity. Do not expand to push/sync/clone for aggregate gains.
