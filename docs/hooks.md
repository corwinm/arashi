# Lifecycle hooks

Arashi runs trusted lifecycle sources during configured `create` and `remove`. A configured logical
location may use either a short inline command from `.arashi/config.json` or one native script file;
examples generated by `aw init` remain inert until activated explicitly. Prefer inline config for
short reviewable commands and native files for substantial, reusable, or independently tested logic.

## Source selection and executable lookup

Only one source may claim a logical location. If an inline source and its native file alternative
claim the same logical location, the location is ambiguous: runtime, remove dry-run, and doctor fail
before mutation and execute neither source. Sources at different scopes still compose normally.
Configured repository remove has one logical slot with three possible claims: inline
`repos.<name>.hooks.<lifecycle>`, canonical workspace-owned
`.arashi/hooks/<lifecycle>.<repo><ext>`, or the compatible child-local
`<repo>/.arashi/hooks/<lifecycle><ext>` alias. There is no precedence between these forms. Any two
claims, including two native extensions or both file locations, are one ambiguity and execute
neither source.

On POSIX, a native lifecycle location supports exactly `<name>.sh`. An inline map selects only its
configured `bash` entry, scans non-empty `PATH` entries in order for a regular executable `bash`, and
normalizes the first match to an absolute real path for Bash. Other configured interpreter entries are
Windows-only.

On Windows, native matching is case-insensitive and a location supports exactly one of `<name>.ps1`,
`<name>.cmd`, or `<name>.bat`. Arashi rejects multiple native candidates before branch, worktree, or
removal mutation and never runs `.sh` implicitly. For inline maps, `%SystemRoot%` supplies only the
fixed system PowerShell and cmd executables; Bash is found by scanning non-empty `PATH` entries in
order for `bash.exe`. Selection is PowerShell → cmd → Bash, with fallback only from an unavailable
higher-priority configured entry to the next configured entry. Empty path entries, invalid or missing
`%SystemRoot%`, `pwsh`, aliases, terminal applications, and unconfigured interpreters are not
fallbacks. The selected path is absolute and normalized. If no compatible configured interpreter is
available, preflight fails with `interpreter_unavailable` before lifecycle mutation.

Native PowerShell files use system
`powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File <path>`; inline PowerShell uses the
same fixed executable with `-Command <snippet>`. Native command files use system
`cmd.exe /d /e:on /v:off /s /c call <encoded-path>`; inline cmd uses the corresponding hardened
`/c <snippet>` adapter. Inline Bash uses `bash -c <snippet>`.

## Terminal input

`ARASHI_HOOK_INPUT` is executor-owned and is always `tty`, `disabled`, or `unavailable`. An eligible human `create` or `remove` invocation gets `tty` only when stdin is a usable terminal. In TTY mode Arashi inherits terminal stdin while keeping stdout and stderr piped for immediate raw prompt streaming and exact internal capture.

`--no-hook-input` is an invocation-only input opt-out shared by `create` and `remove`; it does not
skip hooks. `--no-hooks` is create only: it disables both inline and file discovery, preflight, and
execution after configuration validation. Remove does not provide `--no-hooks`. Create's unrelated
`--interactive` option controls repository selection. `--json` takes precedence and sets disabled
mode. Both disabled and unavailable modes provide immediate EOF rather than an open pipe, so
automation cannot hang on a prompt. There is no persistent `hooks.input` setting.

Use native input primitives: Bash `read`, PowerShell `Read-Host`, and cmd `set /p`. Check `ARASHI_HOOK_INPUT` first and handle EOF explicitly. Never enter a password, token, or other secret through a hook prompt because terminals, transcripts, and hooks may expose it.

## Configured create lifecycle

Inline sources occupy the same lifecycle boundaries, timing, cwd, target multiplicity, and outcome
order as their file alternatives:

1. Workspace `pre-create` runs once, before branch or worktree mutation, from the workspace root.
2. Each selected repository is materialized.
3. Repository-specific `pre-create.<repo>` runs from the new child worktree after it is materialized and before repository setup.
4. Repository-specific `post-create.<repo>` runs next from that worktree.
5. Workspace `post-create` runs once after coordinated Git creation and before move-changes, switch, or launch handling.

Root `hooks.scripts.pre-create|post-create` owns the workspace locations;
`repos.<name>.hooks.pre-create|post-create` owns the corresponding repository locations. The
repository-specific public name remains `pre-create.<repo>` or `post-create.<repo>`, but that encoded
name is not a configuration key. A validation failure, timeout, or nonzero exit fails create and
enters the owned Git rollback boundary. Results include rollback warnings when cleanup is incomplete.
Configured create does not activate repository-local or user-global hooks with similar names.

## Configured remove lifecycle

For each selected repository, inline and file alternatives retain the established repository →
workspace → global repository-targeted → global shared order:

1. repository: `repos.<name>.hooks.<lifecycle>` inline, canonical `<workspace>/.arashi/hooks/<lifecycle>.<repo><ext>` file, or compatible `<repo>/.arashi/hooks/<lifecycle><ext>` file (cwd: child source checkout);
2. workspace: root `hooks.scripts.<lifecycle>` inline or `<workspace>/.arashi/hooks/<name><ext>` file (cwd: workspace root);
3. global repository-targeted: `~/.arashi/hooks/<repo>/<name><ext>` file (cwd: child source checkout);
4. global shared: `~/.arashi/hooks/<name><ext>` file (cwd: child source checkout).

The canonical file is stored under the active configuration root, but its public identity remains the
plain lifecycle name (`pre-remove` or `post-remove`), repository scope, and the named repository owner.
It executes from that repository's active target checkout, not from the configuration root. All
configured remove sources are evaluated once per target repository; inline ownership does not change
workspace/shared multiplicity to once per command. A `pre-remove` failure gates all destructive
removal mutation. After pre-remove succeeds, Arashi revalidates the authoritative plan. `post-remove`
runs after all removal attempts, continues across failures, and participates in partial-failure
finalization rather than create-style rollback.

## Configured repository deletion

`aw delete <repository>` removes only exact workspace-owned `pre-create.<repository>`,
`post-create.<repository>`, `pre-remove.<repository>`, and `post-remove.<repository>` native hook
candidates plus each concrete `.example` template formed by appending `.example` to an exact native
candidate path. Generic `<repo>`/`REPO` templates and shared workspace hooks are not selected. A
compatible child-local remove hook disappears only as part of its owned clone or worktree; it is not
treated as a separately owned workspace hook. Repository-specific user-global hooks are preserved and
reported as guidance; all other user-global hooks are preserved as well. Plans and results expose hook
identity/path/status, never file contents or inline command bodies.

## Standalone lifecycle

Standalone lifecycle support is file-only: zero-config standalone create and remove use only targeted
and shared user-global native file locations, in targeted-before-shared order. Inline configuration is
not available without a valid configured workspace. Targeted lookup uses the resolved main-root
basename even when invocation starts in a linked worktree. Every standalone hook runs from the
resolved main root. Repository-local `.arashi/hooks` content is inactive without configured workspace
state.

Standalone pre-create and pre-remove failures occur before mutation. Standalone post-create failure enters create rollback; post-remove failure preserves completed removal attempts and returns failure.

## Environment contract

Every executed hook receives:

- `ARASHI_HOOK_NAME`: logical discovered name;
- `ARASHI_HOOK_SCOPE`: `workspace`, `repository`, `global-repository`, or `global-shared`;
- `ARASHI_HOOK_EXECUTION_PATH`: exact process cwd;
- `ARASHI_HOOK_WORKSPACE_MODE`: `configured` or `standalone`;
- `ARASHI_MAIN_REPO_PATH`: canonical workspace/main root;
- `ARASHI_BRANCH_NAME`: create branch, or an unambiguous current remove-target branch.

A file source additionally receives `ARASHI_HOOK_SOURCE_PATH` as its exact absolute script path. An
inline source omits `ARASHI_HOOK_SOURCE_PATH`; it receives no replacement containing the snippet.

Targeted invocations additionally receive `ARASHI_HOOK_TARGET_REPOSITORY`, `ARASHI_HOOK_TARGET_REPO_PATH`, and, when unambiguous, `ARASHI_HOOK_TARGET_WORKTREE_PATH`. Only configured repository-specific create receives `ARASHI_PARENT_REPO_PATH`.

Configured workspace create is untargeted: target variables, `ARASHI_REPO_NAME`, and worktree aliases are omitted; historical `ARASHI_REPO_PATH` is the workspace root. Repository-specific create uses the new child worktree for historical `ARASHI_REPO_PATH` and `ARASHI_WORKTREE_PATH`. Remove uses the current child source checkout for `ARASHI_REPO_PATH`, and standalone uses its main root.

### Shell-native fail-fast examples

Use each shell's own environment syntax and make multi-command snippets fail fast so a later success
cannot mask an earlier failure. For Bash, use `$ARASHI_*` variables and `set -e`:

```bash
set -e
printf 'hook=%s cwd=%s\n' "$ARASHI_HOOK_NAME" "$ARASHI_HOOK_EXECUTION_PATH"
./scripts/prepare-hook
```

For PowerShell, use `$env:ARASHI_*` variables and `$ErrorActionPreference = 'Stop'`:

```powershell
$ErrorActionPreference = 'Stop'
Write-Output "hook=$env:ARASHI_HOOK_NAME cwd=$env:ARASHI_HOOK_EXECUTION_PATH"
./scripts/prepare-hook.ps1
```

For cmd, use `%ARASHI_*%` variables and test `errorlevel` after every command:

```batch
@echo off
echo hook=%ARASHI_HOOK_NAME% cwd=%ARASHI_HOOK_EXECUTION_PATH%
call scripts\prepare-hook.cmd
if errorlevel 1 exit /b %errorlevel%
```

Do not put secrets in inline snippets or hook input. Use a secret manager that supplies narrowly scoped
runtime credentials without committing or printing them.

### Remove aggregates

`ARASHI_REMOVE_TARGETS_JSON` is canonical. It contains sorted, deduplicated records:

```json
[
  {
    "repository": "api",
    "branchName": "feature/auth",
    "worktreePath": "/workspace/.arashi/worktrees/feature/auth/repos/api"
  }
]
```

Paths are absolute, lexically normalized, and use `/` separators. Null is used for absent branch/path values. Ambiguous scalar branch/worktree variables are omitted.

The comma-separated `ARASHI_REMOVE_TARGET_BRANCHES`, `ARASHI_REMOVE_TARGET_WORKTREES`, and `ARASHI_REMOVE_TARGET_REPOSITORIES` plus matching `ARASHI_REMOVE_TOTAL_*` counts are lossy compatibility fields. Commas in names or paths are not reversible; new scripts must parse JSON.

Historical `ARASHI_REPO_NAME`, `ARASHI_REPO_PATH`, `ARASHI_WORKTREE_PATH`, and comma-separated remove fields remain supported throughout 1.x and may be removed no earlier than 2.0 through a separately approved breaking change. `ARASHI_BRANCH` and `ARASHI_BASE_BRANCH` are not compatibility aliases.

## Timeout, automation, and outcomes

Inline and file sources share the effective `hooks.timeout`: all lifecycle hooks default to `300000`
milliseconds, and configured workspaces may set an integer from 1 through 2147483647. The timeout
includes time waiting for terminal input. Invalid values fail configuration validation before
discovery or mutation.

JSON mode owns quiet behavior: it suppresses human progress and hook stream output, supplies immediate
EOF, and writes exactly one JSON document to stdout. Human and JSON create/remove output derives from
an ordered per-hook ledger. JSON success places records at `data.hookOutcomes`; command failure places
the evaluated fail-fast prefix at `error.details.hookOutcomes`. Remove post-hook outcomes continue
through finalization. Records distinguish skipped/not-found, validation failure, unavailable
interpreter, timeout, and nonzero exit.

Every public outcome identifies `sourceKind`, `sourceOwnerKind`, `sourceOwnerName`, and
`sourceScriptPath`. `sourceKind` is `file` or `inline-config`; repository ownership names the canonical
repository, while other owner names are `null`. A file has an absolute `sourceScriptPath`; for an
inline source, `sourceScriptPath` is `null`.

`aw remove --dry-run` resolves and validates the real source plan without execution. Its preview
includes inline/file source kind, owner, lifecycle, scope, target, selected interpreter, and a file
path only when applicable; it fabricates no execution outcome. Configured `aw create --dry-run`
does not discover or preflight hooks, returns an empty `hookOutcomes` ledger, and has no hook-preview
surface.

`aw doctor` inspects the same configured repository remove candidate set as runtime and dry-run. An
ambiguity reports de-duplicated `sourceScriptPaths` in canonical-workspace then compatible-child order,
and in `.ps1`, `.cmd`, `.bat` order within each Windows location. The array is bounded to two paths on
POSIX and six on Windows. The compatible nullable `sourceScriptPath` remains populated only when one
native path is sufficient to identify the file claim.

Configured snippet text is never included or derived in human output, quiet output, JSON, logs,
outcomes, previews, doctor findings, warnings, errors, debug data, or environment metadata. These
surfaces report only the non-secret source and target metadata needed to diagnose the logical hook.

## Safe activation and package setup

Activate one POSIX example at a time:

```sh
install -m 755 .arashi/hooks/pre-create.sh.example .arashi/hooks/pre-create.sh
install -m 755 '.arashi/hooks/post-create.<repo>.sh.example' .arashi/hooks/post-create.api.sh
install -m 755 '.arashi/hooks/pre-remove.<repo>.sh.example' .arashi/hooks/pre-remove.api.sh
install -m 755 .arashi/setup.sh.example .arashi/setup.sh
```

On Windows, init generates both PowerShell and cmd lifecycle examples. Activate exactly one native
candidate per lifecycle location: for example,
`Copy-Item .arashi/hooks/pre-create.ps1.example .arashi/hooks/pre-create.ps1` or
`Copy-Item .arashi/hooks/pre-create.cmd.example .arashi/hooks/pre-create.cmd`. Runtime also accepts a
user-authored `.bat` candidate, but do not activate a PowerShell, cmd, and bat definition for the same
lifecycle location. Windows init does not generate a setup script because setup discovery remains
POSIX-only. Generated examples do not automatically infer npm from `package.json`; follow the
repository's committed `packageManager` and lockfile. In a coordinated pnpm child worktree use:

```sh
CI=true corepack pnpm --ignore-workspace install --frozen-lockfile
```
